# Agent Reach — Екосистема агентів

## Мета

Цей документ описує принципи, за якими майбутні проєкти в екосистемі
Agent Reach можуть доповнювати одне одного, комбінуватися між собою
і перевірятися на сумісність. Це не інструкція для терміналу і не
опис конкретної реалізації — це концептуальна карта, яку варто
прочитати перед тим, як починати новий проєкт, щоб він природно
вписався в екосистему, а не став ізольованим острівцем.

## Три рівні сумісності

Коли два агентні компоненти мають "працювати разом", сумісність
перевіряється на трьох незалежних рівнях:

1. **Протокол** — чи говорять компоненти однією версією MCP.
   Клієнт і сервер узгоджують версію протоколу під час
   `initialize`-хендшейку; несумісні версії означають, що
   компоненти не зрозуміють одне одного, навіть якщо API виглядає
   однаково.
2. **Композиція** — як кілька MCP-серверів об'єднуються в одного
   агента: через префікси інструментів, простори імен, проксі-шар.
3. **Виявлення** — як агент дізнається, що потрібний йому інший
   агент чи сервер взагалі існує і де він живе (реєстр, маніфест,
   DNS-подібний механізм).

Ці рівні незалежні: сумісний протокол не гарантує безконфліктну
композицію, а успішна композиція не означає, що агент може бути
знайдений іншими автоматично.

## MCP і A2A — два різні протоколи

- **MCP (Model Context Protocol)** — зв'язок "агент → інструмент",
  вертикальний. Агент викликає інструмент і отримує структурований
  результат. Це те, як агент отримує *можливості*.
- **A2A (Agent-to-Agent)** — зв'язок "агент → агент", горизонтальний.
  Один агент делегує задачу або веде переговори з іншим агентом,
  який має власну автономію та стан. Це те, як агенти *співпрацюють*.

Серйозні багатоагентні системи використовують обидва протоколи
одночасно: MCP — щоб дати кожному агенту доступ до інструментів,
A2A — щоб агенти могли координуватися між собою. Плутати їх —
типова помилка: намагання розв'язати задачу делегування через
інструментальний виклик (MCP) призводить до крихких, монолітних
рішень.

## Композиція через FastMCP

FastMCP пропонує два принципово різні способи об'єднати кілька
MCP-серверів в одного:

- **`import_server`** — статична копія. Інструменти дочірнього
  сервера копіюються в батьківський (з префіксом) один раз, під
  час імпорту. Якщо дочірній сервер згодом змінить свій набір
  інструментів, батьківський цього не побачить, доки імпорт не
  повториться.
- **`mount`** — динамічне живе посилання. Батьківський сервер
  проксіює виклики до дочірнього в реальному часі, тож зміни на
  дочірньому сервері одразу відображаються на батьківському.

В обох випадках критично використовувати **простори імен**
(префікси на кшталт `agent_reach:read`), щоб інструменти з різних
серверів не конфліктували за іменами.

## Реєстри для виявлення

Щоб агент міг знайти сервер, а не лише підключитися до вже
відомого, існують реєстри:

- **Офіційний MCP Registry (Anthropic)** — централізований каталог
  публічних MCP-серверів.
- **Glama, Smithery, AWS Agent Registry** — незалежні та хмарні
  каталоги з власними правилами лістингу та пошуку.
- **Маніфест `server.json`** — стандартизований опис сервера
  (ім'я, версія, можливості, залежності), який реєстри читають для
  індексації та який клієнти читають для перевірки сумісності
  перед підключенням.

## Чекліст сумісності нового агента

Перед тим як додавати новий агентний компонент в екосистему,
перевірити:

- [ ] Унікальний простір імен для інструментів (наприклад,
      `agent_reach:read`, а не голе `read`)
- [ ] Структурований I/O — вхід і вихід описані JSON Schema, а не
      довільним текстом
- [ ] Маніфест з версією та явно перерахованими залежностями
- [ ] Сумісна версія MCP-протоколу з рештою екосистеми

## Поточний стан Agent Reach

- `my_mcp_server.py` — власний MCP-сервер (агент → інструменти),
  надає інструменти `read`, `transcribe`, `status`
- Підключений до: рідного агента (DeepSeek) і Claude Code
- `transcriptor` — хостований MCP-сервер для транскрипції відео
  (YouTube, X/Twitter, Instagram, TikTok, Twitch, Vimeo та інші)
- Локальна транскрипція — резервний шлях через yt-dlp + ffmpeg +
  whisper.cpp, коли хостований сервіс недоступний або субтитрів
  немає

## Що НЕ робити

- **Не використовувати монолітного агента.** Один агент, що
  намагається сам робити все — читання, транскрипцію, статус,
  пошук — не масштабується і не композирується з іншими системами.
- **Не будувати кастомні інтеграції під кожну пару компонентів.**
  Точкова інтеграція "агент X знає про агент Y напряму" множить
  кількість зв'язків квадратично із кожним новим компонентом.
  Натомість — спільний протокол і реєстр.
- **Не плутати MCP і A2A.** Інструмент — не агент, і делегування
  задачі іншому агенту — не виклик інструмента. Використання
  неправильного протоколу для задачі призводить до крихкої
  архітектури.

## Концепція: DeepSeek-оркестратор + Claude Code через Telegram

Ідея (2026-09-18, від користувача): не окремий Telegram-бот "для Claude
Code" (як згадувалось раніше — відкладено), а обгортка навколо чату з
DeepSeek, яка сама делегує задачі Claude Code через A2A-подібний шар
(див. розділ "MCP і A2A" вище) — це і є той самий "агент вищого
порядку", про який каже CONTEXT.md.

Підтверджено (2026-09-18, WebSearch): A2A (Agent2Agent) — реальний
відкритий протокол Google, переданий Linux Foundation, прийнятий
150+ організаціями станом на квітень 2026 — саме для делегування
задач між агентами. LangGraph checkpointing — реальний паттерн для
збереження стану на кожному кроці з можливістю відновлення після
збою і "human-in-the-loop" паузами — релевантний для пункту про
керування контекстом нижче.

### З чого складається
1. **Telegram як інтерфейс** — спілкування з DeepSeek у звичному чаті,
   без термінала.
2. **DeepSeek-чат як оркестратор** — веде розмову з користувачем,
   формулює промти для Claude Code, отримує результат назад.
3. **Claude Code як виконавець** — вирішує технічні задачі (аналогічно
   тому, що DeepSeek MCP уже робить зараз як під-сесія — див. RULES.md
   "DeepSeek — вибір інструменту").
4. **Керування контекстом** — обгортка стежить за заповненням контексту
   DeepSeek-чату і сама переводить у новий чат, коли потрібно, без
   втрати важливого (той самий принцип, що вже реалізований у цій
   сесії через checkpoint CONTEXT.md + baton_pass, тільки для іншого
   чату).
5. **Постійний цикл рефлексії під час задачі** — не тільки виконати,
   а й проаналізувати: чи покращення можливе, чи була схожа помилка
   раніше (перевірка на кшталт TROUBLES.md, тільки автоматична, а не
   ручний grep).
6. **Нагадування** — обгортка сама підказує користувачу важливе, коли
   настає момент (аналог baton_pass, але ініціативний, не за запитом).

### Зв'язок з наявним
- Telegram-бот для Claude Code вже згадувався в CONTEXT.md
  ("Відкриті питання") — ця концепція його замінює конкретнішим
  баченням.
- A2A-шар делегування вже є в BACKLOG.md ("Дослідити") — саме цей
  протокол, а не MCP, потрібен для зв'язку DeepSeek↔Claude Code.
- TROUBLES.md вже виконує роль "чи ми вже з цим стикались" — ідея
  в тому, щоб це стало автоматичною перевіркою, а не ручним кроком.

### Ризики — що може піти не так через рік (2026-09-18)
1. **Автоматичне "чи ми вже це вирішували" (п.5) — небезпечна
   спрощеність.** Семантичне зіставлення нової помилки зі старими
   може дати хибний збіг: система вирішить "уже бачили" для схожої,
   але насправді іншої проблеми, і пропустить реальне розслідування.
2. **DeepSeek як оркестратор без перевірки власних інструкцій.**
   DeepSeek уже падав цієї сесії (permission, timeout). Немає шару,
   що перевіряє промт від DeepSeek до Claude Code перед виконанням —
   хибна інструкція піде далі без контролю.
3. **Автоматична ротація контексту може тихо губити важливе.**
   Той самий ризик, що ми виявили з ручним baton_pass цієї сесії
   (агент вирішує, що важливо, без показу diff), тільки повністю
   автоматизований — без людини, яка побачить різницю.
4. **Секрети — новий вектор.** Telegram-бот потребує власного токена
   (ще один ключ поруч з agent.py і DeepSeek API key) — ще одна точка
   витоку.
5. **Немає kill switch.** Якщо оркестратор зациклиться або дасть
   Claude Code погану інструкцію — немає опису, як це перервати
   негайно.
6. **Дрейф версій за рік.** pip `mcp` пройшов з 1.30 до 2.2.0 за
   кілька тижнів цієї сесії. DeepSeek API, MCP-протокол, Claude Code —
   усе змінюється; концепція не описує перевірку сумісності з часом.
7. **"Нагадування" (п.6) без конкретного тригера — не буде
   реалізовано.** "Коли настає момент" не визначає сигнал (час?
   подія? ключове слово?) — розмиті пункти без тригера традиційно
   не доходять до реалізації.

### Дебати між агентами (п.5) — критерії та ефективність (2026-09-18)

Перевірено власним тестовим дебатом (2 агенти, 2 раунди) + дослідженнями
в інтернеті. Ключова знахідка: **дебати не завжди ефективніші за просте
голосування**.

**Порівняння підходів:**

| Підхід | Що це | Точність vs один агент | Вартість |
|---|---|---|---|
| Один агент | Питаєш один раз | база | найдешевше |
| Голосування (Majority Vote) | Питаєш 2-3 рази НЕЗАЛЕЖНО, береш найчастішу відповідь | часто майже так само добре, як дебати | дешевше за дебати |
| Повний дебат | Агенти сперечаються, бачать відповіді одне одного | +5-40% залежно від задачі | найдорожче (найбільше токенів/часу) |

Дослідження "Debate or Vote" (2508.17536): виграш дебатів здебільшого
йде не від "суперечки" самої по собі, а від опитування кількома
"головами" — це можна отримати дешевше просто голосуванням.

**Критерії якісного дебату (якщо колись реалізовувати повноцінно):**
1. Незалежна відповідь перед взаємодією (Раунд 0 — агенти НЕ бачать
   один одного, щоб уникнути упередження зі старту)
2. Адаптивна кількість раундів, не фіксована — приріст точності росте
   до ~3-4 раунду, далі плато; "хибний консенсус" (обидва помиляються,
   але узгоджено) найнижчий на раунді 2 (3.9%), знову росте до раунду 5
   (5.1%) — більше раундів не завжди краще
3. Окремий суддя для консенсусу, не самі дебатери
4. Застереження: переконливий, але хибний аргумент може перемогти
   правильний ("vivid but incorrect" ефект) — точність може навіть
   ПАДАТИ під тиском узгодження (сикофантія)

**Практичний висновок для п.5 ("постійний цикл рефлексії"):** замість
повноцінних дебатів — простіше й дешевше опитати DeepSeek те саме
питання 2-3 рази незалежно і звірити відповіді (голосування), а не
будувати дорогий механізм дебатів, який не гарантовано ефективніший.

### Статус
Концепція, не план реалізації. Технічні деталі (як саме автоматизувати
кожен з 6 пунктів, і як закрити 7 ризиків вище) — дописувати сюди в
міру появи ідей.
