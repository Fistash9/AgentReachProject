# Request Brief (Agent Reach) — прототип v0

## Навіщо

Мета користувача: щоб запит простими словами давав результат не гірший за якісний промпт з деталями. Дослідження (ECOSYSTEM.md, розділ про перевірку розуміння запиту) показало: моделі розпізнають неоднозначність, але самі рідко перепитують; тому "будь уважнішим" не працює — потрібен явний крок із фіксованою формою. Ця skill і є цим кроком: перетворює короткий запит на 7 рядків, які користувач може підтвердити чи виправити ДО роботи, і дає критерій, проти якого результат звіряється ПІСЛЯ.

## Крок 1 — Бриф (до роботи)

Спершу перевір те, що можна перевірити самому (ls, git status, cat) — не питай користувача про факти, які є у файлах. Потім покажи бриф у такій формі (не більше ~8 рядків, мовою користувача):

```
Розумію так: <1–2 речення>
Мета: <навіщо це користувачу>
Умова зупинки: <коли я зупиняюсь і звітую>
Межі: <що не чіпаю; що лише читаю>
Готово, коли: <перевіряємий факт + чим перевірю: команда, файл, diff>
Припускаю: <що я вирішив сам, чого користувач не казав> (або "нічого")
Питання: <максимум 1, лише якщо відповідь змінює роботу> (або "немає")
```

Правила:
- "Готово, коли" — це факт, який можна перевірити (вивід команди, кількість рядків у diff, наявність файлу), а не "зроблено якісно".
- "Припускаю" — головне поле: саме тут видно хибне прочитання запиту. Не залишай його порожнім із ліні; якщо припущень справді немає — напиши "нічого".
- Якщо є "Питання" — зупинись і чекай відповіді. Якщо питання немає, але робота нетривіальна — усе одно чекай підтвердження брифу.
- Для деструктивних дій (видалення, git push, зміна залежностей/конфігурації) — додай повний перелік "дозволено / заборонено" (правило CLAUDE.md); правила видалення файлів (TRASH.md, `.trash/`) — розділ "Видалення файлів" у CLAUDE.md.
- Якщо запит у деталях суперечить RULES.md чи CLAUDE.md — скажи про це в "Припускаю", а не мовчки обирай сторону.

## Крок 2 — Робота

Роби тільки те, що в межах підтвердженого брифу. Якщо в процесі з'явилось щось поза межами (нова дія, нове припущення) — зупинись і онови бриф, а не розширюй роботу тихо.

## Крок 3 — Звірка (після роботи)

Для кожного пункту "Готово, коли" покажи доказ (вивід команди чи факт із файлу) і статус: ✅ підтверджено / ❌ не збігається / ⚪ не перевірено. Потім окремим рядком — "Розбіжності з брифом": що зроблено понад бриф, що не зроблено, що змінилось у припущеннях. Не пиши "готово" без доказу; якщо критерій неможливо перевірити — скажи це прямо.

## Чого ця skill (v0) НЕ робить

- **Не запускається автоматично.** Спрацьовує лише на збіг з description або виклик вручну. Автозапуск (наприклад, UserPromptSubmit-хук) не реалізований; прецедент — Unlazy Stop-хук, який без прив'язки жодного разу не спрацював сам.
- **Не доведено, що покращує результат.** Перевірено тільки на реконструйованих випадках з однієї сесії; такий тест схильний до упередження заднім числом. Справжня перевірка — жива робота на наступних запитах.
- Не замінює правило пам'яті "спершу переказати розуміння" — доповнює його полями "Готово, коли" і "Припускаю" та кроком звірки.
