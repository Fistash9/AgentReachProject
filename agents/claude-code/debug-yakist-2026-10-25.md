# Дебаг, якість коду, навчання на помилках: що є в нас і що є готове (2026-10-25)

— [claude-code, 2026-10-25; запит користувача: «пункти дебаг, ти працюєш по ним, думаю вже є інструкції як писати гарний і якісний код, як шукати помилки і вчитись на них, так же?»]

Мета: знайти готові перевірені інструкції для дебагу, якості коду й навчання на помилках; порівняти з нашими. Нічого не встановлено, не змінено, крім цього файлу.
Позначки: [перевірено] = відкрито цієї сесії; [не перевірено] = не відкривав сам.

## Коротко
- Так, готові інструкції є, і вони збігаються з нашим порядком дебагу. Найповніше — superpowers (автор Jesse Vincent, obra), офіційні поради Anthropic та книги Zeller / Agans.
- У нас є правила-тексти про корінь, тест, живу перевірку, але порядок дебагу в RULES.md не записаний (слів «дебаг / відтвори / регрес» там 0 — перевірка користувача), а ворота є тільки для чужих задач (grep TROUBLES перед Bash, перевірка перед показом плану), не для моменту «збій інструмента» чи «перед комітом коду».
- Найбільша діра: немає кроку «регресійний тест на кожен виправлений баг» і немає правила «3 невдалі спроби — стоп, переглянути підхід» як ворота (є лише текст «повтори наосліп» у TROUBLES 25.10).

### A. superpowers — Jesse Vincent (obra) [перевірено]
- URL: https://github.com/obra/superpowers ; скіли: https://github.com/obra/superpowers/tree/main/skills/ (systematic-debugging, test-driven-development, verification-before-completion).
- Автор: Jesse Vincent (obra), команда Prime Radiant (за README). Репозиторій створено 2025-10-09, останній push 2026-10-23, ліцензія MIT, 304 737 зірок (GitHub API, цієї сесії). Скіл systematic-debugging востаннє змінено 2026-07-23 (комміт «find-polluter accepts ./-prefixed patterns»), реліз v7.0.0 від 2026-10-10.
- Відгуки/issues: сторінка Issues показує 185 відкритих (API: open_issues_count 358 — це issues разом із PR; розбіжність не розбирав). Найсвіжіші — про довгі сесії subagent-driven-development (#2612: контекст 830k токенів), про TDD (#2557 «blind spots», #2546, #2539), про bug-reports у brainstorming (#2576: дає «перепитай і підтверди» замість розслідування). Про systematic-debugging відкритих issues у переглянутій частині списку не побачив. Незалежних оглядів/рецензій не шукав [не перевірено]. Є запит «support for a DeepSeek harness» (#2575).
- Що радить systematic-debugging (SKILL.md, прочитано):
  1. Залізний закон: «NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST».
  2. Фаза 1: прочитати повну помилку, відтворити стабільно, переглянути останні зміни, зібрати докази на межах компонентів, простежити дані назад до джерела.
  3. Фаза 2: знайти робочий приклад, перелічити всі відмінності між робочим і зламаним.
  4. Фаза 3: ОДНА конкретна гіпотеза, перевірка найменшою зміною; не вийшло — нова гіпотеза; чесно сказати «не розумію».
  5. Фаза 4: спершу падаючий тест, одне виправлення кореня, без побічних змін, перевірка перед «готово».
  6. Правило невдач: після ≥3 невдалих виправлень — «STOP and question the architecture».
- test-driven-development: «NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST»; червоний → зелений → рефакторинг; перевір, що тест падає з очікуваної причини; «A green run of the test you wrote is not a green suite»; «Never fix bugs without a test».
- verification-before-completion: «NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE»; визначити команду-доказ, запустити свіжою, прочитати вивід і код виходу, лише тоді стверджувати; «should/probably» — червоний прапор.
- Обмеження: це методика для розробки ПЗ з тестами; наш проєкт — переважно хуки, Python-скрипти, документи. Повна методика (brainstorm → план → підагенти) важка і конкурує з нашими request-brief/unlazy; брати окремі скіли, не весь пакет.

### B. Anthropic — Claude Code best practices [перевірено]
- URL: https://code.claude.com/docs/en/best-practices ; https://code.claude.com/docs/en/common-workflows (розділ Fix bugs efficiently). Автор: Anthropic (офіційна документація).
- Що радить:
  1. «Give Claude a way to verify its work»: тест, збірка, лінтер, скрипт-порівняння; показувати докази (вивід тесту), не заяви.
  2. Приклад промпту «Address root causes, not symptoms»: «fix it and verify the build succeeds. address the root cause, don't suppress the error».
  3. Приклад «Describe the symptom»: симптом + місце + що значить «виправлено»; «write a failing test that reproduces the issue, then fix it».
  4. Дебаг: дати команду для відтворення і stack trace, сказати, чи помилка плаваюча (common-workflows).
  5. Жорсткі ворота: Stop-хук, що не дає завершити хід, поки перевірка не пройде; `/goal` з незалежним оцінювачем; «hooks are deterministic» на відміну від CLAUDE.md, що «advisory».
  6. «Adversarial review»: рецензент у свіжому суб'єкті, лише про коректність, не про стиль (бо інакше надмірна інженерія); `/code-review` як вбудований варіант.
  7. «If you've corrected Claude more than twice on the same issue… /clear» — аналог нашого «3 невдачі».
- Відгуки: це першоджерело виробника, окремих відгуків не шукав [не перевірено].

### C. Науковий метод дебагу — Andreas Zeller, «Why Programs Fail» / The Debugging Book
- URL: https://www.debuggingbook.org/html/Intro_Debugging.html [перевірено]; книга: https://shop.elsevier.com/books/why-programs-fail/zeller/978-0-12-374515-6 [перевірено сторінку пошуку, не книгу].
- Автор: Andreas Zeller (розділ вказує його як автора).
- Що радить (прочитано): цикл «питання → гіпотеза → передбачення, що може її спростувати → експеримент → повторювати, поки гіпотеза, передбачення й спостереження не збігаються»; «Check your Tests»: якщо тести не знайшли дефект, «add a test that catches the bug (as well as similar ones)» — проти регресій; «Debugging Aftermath»: коментар біля виправлення, чому код такий, щоб не повернути баг.

## (4) Пропозиція: один чек-лист і коли він спрацьовує

Чек-лист «Дебаг-8» (один, 8 рядків, формат для розмови — відповідь на кожен рядок коротко з доказом команди):
1. Відтворив? (команда і її вивід)
2. Дані: що кажуть лог/зміни? (рядок із лога, `git log`)
3. Гіпотеза одним реченням + що її спростує
4. Одна зміна — один експеримент (результат)
5. Виправив причину, не симптом («Звідки:» з доказом)
6. Регресійний тест або simulate-вхід, що падав до і пройшов після
7. Перевірив тим самим викликом, яким викликає справжній процес, вивід показаний
8. Урок: запис у TROUBLES (клас, ліки, як перевірити, що ліки діють)
Плюс стоп-правило: 3 невдалі спроби поспіль → не четверта спроба, а крок 2 заново і питання користувачу.
