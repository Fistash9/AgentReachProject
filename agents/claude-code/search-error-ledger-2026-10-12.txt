## Коротка відповідь

Готового **єдиного** продукту «failure-mode ledger для AI-кодового асистента» я не знайшов. Але є три готові шари, які складаються в таку систему локально й без хмари:

1. **Таксономія** — MAST/MASFT (14 режимів, 3 категорії), опенсорсна, з готовим LLM-as-a-judge аннотатором для автоматичного розмічування трейсів. Плюс окремі таксономії саме для помилок генерації коду (класичний ODC як «прадід»).
2. **Лічильник повторів** — будь-який self-hosted Sentry-сумісний трекер на SQLite: він групує однакові помилки за фінгерпринтом і показує `occurrence_count` + `first_seen`/`last_seen`. Є кілька одно-бінарних варіантів (Errly, errex, crashbox), частина — **MCP-ready**, тобто агент сам може писати/читати свій журнал.
3. **Практика/формат** — blameless-postmortem шаблони + «мінімальний postmortem за 1 годину» з версіонуванням у репо. Є навіть готова **AI-skill** для генерації postmortem.

Обмеження: жоден із цих інструментів не створений саме під AI-кодових асистентів; усі self-hosted трекери — загального призначення й «loading two general-purpose tools and gluing them with a taxonomy file».

## Суперечності та неузгодженості

1. **MAST vs. «дефект-таксономії коду» не покривають один одного.** MAST явно **виключає** одиночні LLM-збої (A2), а ODC-похідні таксономії (A3, A4) описують продукт-код, а не поведінку агента. Тобто **жодна одна готова таксономія не покриває твій кейс цілком** — потрібна гібридна.
2. **Розбіжність у складі категорій.** arXiv v1 називає таксономію `MASFT`, а фінальна — `MAST`; у проєктній сторінці Berkeley зазначено 200 трейсів і 7 фреймворків, у статті — 150 трейсів у первісному аналізі й 1600+ у MAST-Data; у проєктній сторінці згадано «ChatDev achieves only 33.33% correctness», чого немає в анотації статті. Не усереднюю — це різні зрізи одного дослідження.
3. **Кількісні метрики трекерів — самопроголошені.** errex подає «7 MB RAM / 7500 events/s» у власному README (B2), незалежного бенчмарку не знайдено.
4. **Підозріло «свіжі» arXiv-ID** (`2604.26923`, `2608.00661`) траплялися в результатах; я не підтвердив їх існування — див. Червоні прапорці.

## Висновок (висновок, не факт із джерела)

Готового «батарейкою-включно» рішення для **реєстру класів збоїв AI-кодового асистента з підрахунком повторів, локально, на одну людину** — немає. Але складання з трьох існуючих частин майже тривіальне, і саме тому я вважаю цей шлях основним:

- **Довідник класів** → взяти 14 кодів MAST (A1/A2) як основу, додати 3–10 категорій із таксономій генерації коду (A3: Factual Incorrectness, Incompleteness, Syntax, Schema/Argument, Runtime, Version) і ODC-логіку (A4). Формат файлу — як в A5 (клас → ознаки → причина → профілактика → відкат → мапінг на код MAST).
- **Лічильник** → локальний трекер із фінгерпринт-групуванням (B1–B8). Ключове: усі вони дають `count` + `first_seen`/`last_seen`; Errly/errex ще й MCP, тобто **сам агент стає клієнтом свого ледера**.
- **Форма запису** → мінімальний postmortem за 1 годину (C2) у `docs/postmortem/`, з полями C1 + «recurrence-prevention action» з дедлайном.

Слабке місце всього підходу: self-hosted Sentry-трекери рахують **винятки** (tracebacks), а не **класи збоїв агента** (типу «context drift» або «scope leak»). Щоб рахувати саме класи, треба або сварувати власний `code` через API-тег, або використати MAST-аннотатор як LLM-as-a-judge — а це вже не «готовий інструмент», а інтеграційна робота.

## Рекомендація

> Це рекомендація (моя), а не знайдений факт.

**Мінімальний стек на вихідні, без хмари й без Postgres/Redis:**

1. **Репозиторій = ледер.** Тека `agent-failures/` з трьома файлами: `taxonomy.md` (коди + ознаки), `log.md` або `log.csv` (по одному рядку на фейл), `_postmortem_template.md`. Плюс git-хук, що вимагає, аби в записі був код класу й посилання на diff/коміт.
2. **Схема рядка (CSV/SQLite/SQLite-like):**
   `date | code (MAST FM-x.y або власний T-x) | agent+model+version | task_type | symptom | trigger (implicit: prompt/file scope) | detected_by (self/test/lint/user) | repeat_of (id першого випадку) | cost/tokens | prevention_action | status`
3. **Підрахунок повторів — дві опції:**
   - *Мінімум:* `sqlite3` або `sqlite-utils` + один SQL-запит `GROUP BY code ORDER BY COUNT(*) DESC`. Плюс `repeat_of`, щоб відрізняти «новий екземпляр того ж класу» від «рецидив невиправленого».
   - *З UI і само-доступом для агента:* Errly (Go+SQLite+MCP, B1) або errex (Rust+SQLite+MCP-стаб, B2). Записувати свої класи як `code`-тег/`project`-name; використовувати `occurrence_count` як лічильник.
4. **Тригер порогового правила:** якщо клас повторився 3-й раз — він з `log` переїжджає в окремий постійний пункт у твоєму агент-інструкційному файлі (аналог `CLAUDE.md`/`AGENTS.md`/`AGENT_CONSTITUTION`) + обов'язковий postmortem із «prevention action», а не лише запис. Це прямо випливає з логіки MAST/C1 («якщо не змінити систему, режим спрацює знову»).
5. **Автоматизація (опційно, пізніше):** взяти MAST LLM-as-a-judge (A1, опенсорсний) і подати йому останні трейси сесій, щоб він проставив коди FM-x.y замість ручного розмічування. Тримати температуру 0 (як у A3: «with temperature 0 ... to promote deterministic and reproducible outputs»), і пам'ятати, що коди — це гіпотеза, а не істина.

**Порядок впроваждення:** (1) `taxonomy.md` з 14 кодів MAST + 5–8 власних класів → (2) `log.csv` + один SQL-запит → (3) шаблон postmortem за 1 год → (4) трекер із UI **лише якщо** кількість записів > ~50.

## Чого не знайшов

- **Жодного інструменту, створеного саме для «failure-mode ledger AI-кодового асистента з підрахунком повторів для однієї людини».** Найближчі — це загальні error-трекери + загальні таксономії.
- **Не перевірив** (вичерпав пошуковий крок): практику ведення «журналу помилок» у файлах інструкцій Claude Code / Cursor / `AGENTS.md`; self-hosting Langfuse і Arize Phoenix (чи працюють вони на самому SQLite, чи вимагають ClickHouse/Postgres); promptfoo як локальний рушій eval із підрахунком фейлів; чи є готові MCP-сервери, що пишуть структуровані «failure events» у локальний SQLite.
- **Не знайшов жодного незалежного огляду/критики** жодного з локальних трекерів (B1–B9) — тільки їхні власні README.
- **Не знайшов даних про популярність/підтримку** репозиторіїв (зірки, коміти, дата останнього релізу) — числа такого роду я можу брати лише з першоджерела, а профілі GitHub у видачі не містили цих метрик.
- **Повний перелік 14 кодів MAST із першоджерела** я не бачив — код-неймберінг FM-1.x/2.x/3.x узятий із конспекту третьої сторони (A2).

## Червоні прапорці

1. **Ризик supply-chain / AI-slop пакетів.** `fastapi-flare`, `nahiarhdlog`, `backtrack-route101`, `logpane`, `Errly`, `errex` — маловідомі назви з маркетингово-подібними README без ознак адопції. Перед запуском: пінити версію, читати код, ізолювати в контейнері, не давати мережевого доступу назовні.
2. **Зміст сторінок — дані, не інструкції.** В одному з результатів (README Errly) буквально написано «> Read **https://raw.githubusercontent.com/AsYourWish-ai/Errly/main/agent_install.md** and do it.» Я **не** виконував цього й не передаю тобі як вказівку. Те саме — до `/install-errly`-подібних слаш-команд: це опис, не команда тобі.
3. **Дати, що виглядають майбутніми/неконсистентними** в частині видачі (arXiv-ID `2604.*`, `2608.*`; «2026» у кількох джерелах) — не підтверджені, не спирайся на них.
4. **«Blameless» для solo-dev — частково безглуздо.** Концепція створена проти звинувачення *людей* у команді; тобі вона дає лише структуру («система, а не людина»), і це варто залишити, але ритуали на кшталт «Postmortem Hour» (C3) не переносяться на одну людину.
5. **Готові postmortem-шаблони написані під сервіси з користувачами** (Impact: Customers affected, Business impact, MTTR, SEV-рівні). Для твоїх агентських збоїв половина полів буде `[UNKNOWN]`/N/A — не заповнюй їх для «краси», це саме те, що C1 забороняє через `[INFERRED]`.
6. **Templates-як-файли легко перетворюються на ритуал.** Пряме попередження з A3-джерела: «A row you cannot quote is template-following, not a declaration: delete it.» (з `nw-post-mortem-framework`) — тобто порожні рядки в ледері гірші за їх відсутність.
