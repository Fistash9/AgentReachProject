# Нарада з DeepSeek: як найефективніше працювати з тобою
Автор: claude-code (оркестратор на Claude), 2026-10-01. Вузол T6.2,
trees/pidrozdil-deepseek.md. Мета й контекст — як людині; питання наприкінці —
щоб нічого не загубити.

## Мета
Ми (користувач + оркестратор на Claude у Termux/Android) хочемо ОДИН
досконалий інструмент роботи з тобою, який (1) викликається автоматично
замість кількох теперішніх шляхів, (2) завжди перевіряє висновки оркестратора
як незалежна третя сторона, (3) автоматично скликає «нараду», коли рішення
важливе. Порадься з нами як колега: подумай сам, що з цього розумно, що ні,
і як зробити найкраще. Свої поради підкріплюй першоджерелами з дослівними
цитатами; що не можеш підтвердити — познач [не перевірено]. Ми все звіримо.

## Що є зараз (5 шляхів до тебе)
1. delegate (MCP) → BazaarLink, безкоштовний deepseek-v4-flash; без вебу;
   часто 429 «site-wide free-model capacity is currently full»; ≈170 КБ входу.
2. інструмент `deepseek` (MCP deepseek-mcp) → під-сесія Claude Code на твоєму
   Anthropic-API; за замовчуванням v4-pro + effort max; обгортка ≈21,6 тис.
   токенів на перший запит; WebSearch/WebFetch Claude Code (WebFetch переказує
   сторінку малою моделлю — «lossy by design»; бекенд WebSearch «not
   configurable»).
3. агент deepseek-search (той самий шлях 2, своя тека й інструкція: flash,
   1 WebSearch + ≤4 WebFetch, звіт із розділом «[не перевірено]», 1 855 токенів
   старту).
4. tools/deepseek-search.py — прямий запит до /anthropic/v1/messages: flash,
   thinking enabled, web_search_20250305 max_uses 5, max_tokens 32 000,
   пам'ять розмови в JSON (продовження -c ID), без читання повних сторінок.
5. DSH (DeepSeek Harness 0.2.0-rc.2 у proot) — твоя оболонка: рідний
   web_search (searchProvider deepseek-official) + web_fetch http; кожна
   shell-команда — клік користувача; викликається лише через веб-API 3080.
Автовиклик зараз: глобальний хук classify-task.sh підказує «делегуй на
DeepSeek»; скіл verify-before-show шле твердження через delegate (шлях 1).
Платне — лише після «так» користувача (замок на інструменті `deepseek`).

## Що ми вже знаємо (перевірено нами)
- Рідне в Anthropic-API (api-docs.deepseek.com/guides/anthropic_api):
  server_tool_use і web_search_tool_result — «Supported»; code_execution, MCP,
  container — «Not Supported»; web_fetch — не згадано; thinking «Supported
  (budget_tokens is ignored)»; output_config «Only effort is supported». У
  Responses-API web_search — «Ignored».
- max_tokens рахує й міркування: при 1 200 і 6 000 відповідь була порожня
  (stop_reason max_tokens). Без поля thinking ти думаєш за замовчуванням;
  thinking disabled для механічної звірки — той самий вердикт за 324 вих.
  токени проти 8 843; для діагнозу без мислення вийшло хибно.
- reasoning_content треба повертати, коли в запиті є tools (400 інакше);
  плейсхолдер замість старого тексту мислення проходить (наш проксі).
- Твоя оболонка DSH сама не довіряє прозі пошукової моделі: «content is
  always omitted: DeepSeek's provider prose is not trusted as an answer»;
  бере web_search_result (url, title, page_age) + cited_text; пошук — окремий
  запит «Perform a web search for the query: …», maxUses 5, maxTokens 4096;
  до пошуку додає web_fetch.
- Наш дослід (той самий файл висновків, 2026-10-01, по 1 прогону):
  C1 прямий API + чек-лист: 8 пошуків, 13/13 цитат справжні, 8 нових
  джерел, 4 помилки суджень. C-мета прямий API + «людський» запит (мета без
  чек-листа): глибші 5 зауважень до логіки, але 2 фактичні помилки й 4 хибні
  «не знайшов». B-мета шлях 3: 0 помилок у звіреному, чесне «[не
  перевірено]», ~0 нових джерел, ~146 с. Разом ≈$0.06. У всіх трьох прямих
  викликах usage.server_tool_use.web_search_requests = 8 при max_uses 5.
- Баланс списується із запізненням (хвилини), тож ціну одного виклику
  точно видно лише згодом.

## Питання наради
1. Як найкраще викликати тебе для ПЕРЕВІРКИ висновків як незалежної третьої
   сторони: один запит чи два кроки (пошук → вердикт), який стиль запиту
   (мета, чек-лист, обидва), чи показувати тобі міркування оркестратора, чи
   лише твердження з джерелами (щоб не упередити)?
2. Як отримати повний текст сторінок, коли web_fetch у тебе немає: наш
   curl-крок, чи є інший рідний спосіб?
3. Чи дотримуєш ти max_uses, і як ще керувати кількістю пошуків і
   глибиною мислення (effort, thinking) без втрати якості?
4. Як зробити «один інструмент» замість 5 шляхів: що з них лишити, що
   прибрати; що робити, коли безкоштовний шлях дає 429.
5. Механізм автовиклику: коли саме скликати тебе автоматично (перед показом
   висновку користувачу? на важливі рішення — «нарада»?), як не витратити
   гроші на дрібниці, як виміряти, що це справді краще.
6. Чого ми не бачимо — ризики, кращі практики, готові рішення інших.
Наприкінці — короткий план «що зробити першим» і що варто виміряти.
