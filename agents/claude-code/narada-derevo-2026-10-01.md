# Нарада з DeepSeek: живе поярусне дерево + пошук DeepSeek замість WebSearch
Автор: claude-code, 2026-10-01. Вузли G2 (trees/derevo-i-golograma.md) і T6.2.

Порадься з нами як колега. Мета: працювати дешевше й прозоріше — щоб уся робота
велася поярусно в живому дереві (кожна тема — окреме дерево, вузли короткі,
деталі окремо, все видно одним поглядом), і щоб агент читав лише свою гілку, а
не великі файли. Подумай сам, що тут розумно, і скажи прямо, якщо щось — ні.

## Як відповідати (наші правила коректності)
- Не вигадуй: кожен факт — з URL і дослівною цитатою з першоджерела
  (документація, репозиторій, стаття важливіші за агрегатори й SEO).

- Суперечності між джерелами назви, не згладжуй.

## Середовище й факти (перевірено нами)
- Android, Termux (bionic libc, без glibc); є proot з Ubuntu (glibc).
  Оркестратор — Claude Code; нагадування активної гілки дає наш хук, що читає
  trees/*.md з позначками [ ] [x] [>] @агент. Два агенти (claude-code, DSH).
- Проблема: картка trees/pidrozdil-deepseek.md — 40 553 байти на 12 вузлів,
  один вузол — 8 705 байтів прози (звіти пишуться прямо у вузол).
- Кандидати:
  1. Backlog.md (github.com/MrLesk/Backlog.md, 6 915★, MIT): задача =
     окремий .md у git; батько/діти (`backlog task create -p`, `task list
     --parent 42`), залежності, віхи; `backlog board` — «live board in your
     shell» (Канбан, не дерево), веб-дошка, `--watch`; MCP для Claude Code,
     `--plain`; «One task = one context window». npm ставить бінарник
     backlog.md-linux-arm64 (зібраний bun) — чи запуститься в Termux, не знаємо.
  2. Beads + beads_viewer bv (1 705★, ліцензія NOASSERTION, Go,
     linux_arm64): дерево/граф залежностей у TUI; Beads у нас працює лише в
     proot (embedded Dolt, CGO), дані поза git, виклик ≈1,2 с.
  3. Свій формат: вузол 1–3 рядки + файл деталей на вузол + скрипт перегляду
     у вікні tmux.
- Дослідження ETH (arXiv 2602.11988): великі файли контексту +20% ціни.
- Пошук: бекенд WebSearch Claude Code «not configurable. To search with a
  different provider, add an MCP server». Твій рідний web_search у нас працює
  прямим запитом (скрипт; ≈$0.01–0.02 за виклик). Сьогоднішній дослід: прямий
  пошук знаходить більше нових джерел, але робить більше помилок суджень, ніж
  дисциплінований агент; WebSearch для оркестратора окремо не платний.

## Питання
1. Що обрати базовою структурою поярусного живого дерева в наших умовах
   (1, 2, 3 чи щось інше, чого ми не бачимо)? Чи взагалі ефективно — є
   виміри? Як зробити, щоб агент читав лише свою гілку?
2. Чи варто замінити WebSearch твоїм прямим пошуком (автоматично через MCP +
   хук), і як: завжди, лише для досліджень, лише для перевірки висновків? Як
   контролювати ціну і помилки?
3. Наприкінці — «що зробити першим» і що виміряти.
