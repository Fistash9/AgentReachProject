# Agent Reach — Правила роботи

## Навігація
- Стан проєкту → CONTEXT.md
- Поточні задачі → BACKLOG.md
- Технічні граблі → TROUBLES.md
- Стан сесії → HANDOFF.md (baton)
- Концепції → ECOSYSTEM.md
- Карта документації → README.md

## Формат взаємодії
- Одна дія — одне повідомлення. Якщо це команда — даю тільки її.
- Складні задачі — розбиваємо на етапи.
- Перед новою дією — grep по TROUBLES.md.
- Для задач Claude Code — давати повний промпт з межами, не покрокові
  інструкції, якщо задача безпечна.
- Структура промпту (принцип з дебатів агентів, 2026-09-18): завжди
  вказувати мету + умову зупинки; повний шаблон "дозволено/заборонено"
  додавати тільки для деструктивних дій (видалення, git push, зміна
  залежностей/конфігурації) — не для будь-якої задачі.

## Заборонено
- Не припускати («скоріш за все»). Спочатку перевірка — потім висновки.
- Не давати кілька команд одночасно.
- Не подавати варіанти як взаємовиключні, поки не з'ясовано потребу.
- Не комітити agent.py (ключ!).
- Перед git add — завжди git status.

## Обов'язково
- Перевіряти факти: ls, grep, npm list, cat — перед тим як щось стверджувати.
- Визнавати помилку одразу, а не «зараз спробуємо ще».
- Перед новою дією — перевірити, чи не зламає вона існуюче.

## Перед рекомендацією пакета/URL
- Перевірити існування пакета: npm view / pip index versions / curl -I
- Перевірити авторство: офіційний проєкт чи сторонній
- Перевірити залежності: чи не конфліктує з mcp<2.0.0
- Якщо не перевірено — позначити "НЕ ПЕРЕВІРЕНО"

## Рівні знань
- **Sourced** — є первинне джерело (URL, документація, репозиторій).
  Включати як факт.
- **Unverified** — агент вірить, але не може вказати джерело.
  Позначати [unverified] inline + виносити в окремий розділ.
- **Hallucinated** — вигадка, є підстави сумніватися. Відкидати.

Правила:
- Якщо можеш процитувати — цитуй.
- Якщо віриш, але не можеш — [unverified].
- Якщо вигадав — опускай.
- Зовнішні твердження (URL, пакети, API) — завжди верифікувати
  або позначати [unverified].
- Твердження про власний код — не потребують веб-верифікації.

## Бекап поза git
- Файли в .gitignore (.env, agent.py, settings.local.json, HANDOFF.md,
  .baton/) НЕ мають git-історії — git checkout/revert їх не врятує.
- Перед зміною такого файлу скриптом/хуком — робити .bak-копію перед
  перезаписом (як Unlazy робить для settings.local.json).
- Для файлів під git (BACKLOG.md, TROUBLES.md, CONTEXT.md, RULES.md) —
  git і є бекап, додатковий .bak не потрібен.

## Checkpoint
- Оновлювати CONTEXT.md ДО стиснення контексту (60-70% заповнення).
- Після кожної сесії — записувати рецепти в TROUBLES.md.

## Робота з відкладеними процесами
- При переході до нового процесу — СПОЧАТКУ перевірити BACKLOG.md:
  чи немає відкладеного, що стосується нової теми.
- Якщо з'являється нова відкладена ідея — одразу записати в BACKLOG.md
  (не тримати в голові, не сподіватись на пам'ять чату).
- Наприкінці сесії — переглянути BACKLOG.md, оновити статуси.

## Запис знань
- Технічні знахідки → TROUBLES.md
- Правила та формат роботи → RULES.md (реальний файл; симлінки
  AGENTS.md → CLAUDE.md → RULES.md — усі три імені ведуть сюди)
- Відкладене → BACKLOG.md
- Стан проєкту → CONTEXT.md
- Концепції → ECOSYSTEM.md
- Ризик "documentation drift" (висновок обговорено в чаті, але не
  записано у файл — тобто для наступної сесії його не існує): перед
  завершенням розмови на важливу тему — перевірити, чи висновок
  реально потрапив у файл, а не тільки прозвучав. Дослідницький
  термін для цього — "Knowledge Crystallization" (arXiv 2603.10808).
  Вбудований Skill `anthropic-skills:zvirka-bazy` уже робить цю
  перевірку автоматично — викликати його, коли не впевнений, чи все
  осіло у файлах.

## MCP-сервери — використання
- **Не використовувати memory MCP** (knowledge graph, 9 tools) для
  щоденної роботи — дублює BACKLOG.md/TROUBLES.md/CONTEXT.md. Toil/
  shelfware-аудит 2026-09-19 показав нуль викликів за сесію. Причина
  зробити виняток має бути конкретною, не "про запас"

## Baton — передача контексту між агентами
- На початку сесії — викликати baton_pick_up, щоб підхопити HANDOFF.md.
- Перед завершенням сесії — викликати baton_pass, щоб передати контекст далі.
- baton_status — для швидкої перевірки, хто останній агент і на чому зупинились.
- .baton/ і HANDOFF.md — локальні (у .gitignore). AGENTS.md — комітиться.

## DeepSeek — вибір інструменту
- Для розмов/рутини — викликати інструмент deepseek (під-сесія на DeepSeek).
- Для важких задач (>300 рядків) — delegate (спрацьовує автоматично через hook).
- Не використовувати deep-claude — ламає MCP (несумісний з DeepSeek Anthropic-шаром).
- Для дослідницьких/пошукових задач через deepseek — одразу передавати
  `permission_mode: "bypassPermissions"` (headless-підпроцес без TTY
  інакше не може отримати дозвіл на WebSearch/WebFetch).
- Для deepseek — розбивати задачі на вужчі виклики: 1-2 файли АБО
  1 web-пошук за раз, не 4+ файли + кілька пошуків одночасно
  (інакше — timeout, exit 143).

## Журнал vs знімок стану
- Журнал/архів (TROUBLES.md, BACKLOG.md "Завершено", CONTEXT.md
  "Оновлення N") — НІКОЛИ не видаляти й не переписувати старі записи,
  тільки дописувати. Якщо запис застарів — дописати нижче примітку
  "статус змінився", а не стирати оригінал.
- Знімок стану (HANDOFF.md, CONTEXT.md "Архітектура"/"Поточний фокус")
  — можна перезаписувати, АЛЕ показати новий текст користувачу ДО
  запису, якщо змінюються факти, а не тільки дописування нового.
- Перед будь-якою правкою, що ВИДАЛЯЄ або СКОРОЧУЄ наявний текст
  (не додає) — показати старий і новий варіант і чекати підтвердження,
  незалежно від того, наскільки "очевидною" здається правка.
